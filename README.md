# Shiyao

**Shiyao (石爻) is a secure, self-hosted infrastructure platform for running AI agent code.**

It runs untrusted agent code inside isolated [Firecracker](https://firecracker-microvm.github.io/) microVMs with per-VM networking, resource controls, and a VSOCK execution API. Snapshot resume and warm instances provide the building blocks for fast, isolated execution.

> **Status:** Shiyao is under active development. The current implementation is an engineering foundation, not a claim of production-ready sandbox security. Run the privileged integration tests against the exact kernel, Firecracker, nftables, and cgroup configuration you intend to deploy.

## Why Shiyao?

AI agents increasingly need to execute code, install packages, manipulate files, and access external services. That code should be treated as **untrusted** even when it was generated by an otherwise trusted agent.

Shiyao is designed around a simple boundary:

```text
trusted control plane
        |
        | lifecycle + execution API
        v
untrusted guest workload
```

The guest is isolated in a Firecracker microVM, network forwarding is default-deny, command execution is bounded, and VM admission is controlled by explicit capacity limits.

The performance goal is to make isolated execution practical for interactive agent workloads. Shiyao includes both snapshot-resume support and warm-instance pooling, while keeping cold boot vs. snapshot-resume benchmarking as an explicit concern rather than assuming a particular latency.

## Architecture

```text
AI agent / application
        |
        v
+-----------------------------+
|       Shiyao control plane  |
|                             |
|  admission / lifecycle      |
|  network policy             |
|  execution API              |
+--------------+--------------+
               |
               v
      +-------------------+
      | Firecracker VM    |
      |                   |
      | guest agent       |
      |       ^           |
      |       | VSOCK     |
      +-------+-----------+
              |
              v
        per-VM TAP device
              |
              v
        shared nftables
        default-deny policy
```

### Core components

- **VMM management** — Firecracker lifecycle management, including create, start, stop, and snapshot resume.
- **Network isolation** — per-VM TAP devices with shared nftables policy and default-deny forwarding.
- **VSOCK execution** — bounded command execution with request validation, concurrency limits, output limits, and optional framed stdout/stderr streaming.
- **Admission control** — limits on resident VMs and concurrent provisioning operations.
- **Warm pooling** — reuse of prepared running instances with caller-supplied reset operations.
- **Snapshots** — snapshot resume support plus cold-boot vs. snapshot-resume benchmarking.

## Security model

Shiyao's primary security assumption is that **guest workloads are untrusted**.

The control plane owns VM lifecycle and network policy. Guests communicate with the host through the VSOCK execution boundary and use a per-VM network interface subject to the shared nftables policy.

The main controls currently implemented are:

- Firecracker microVM isolation.
- Default-deny forwarding for managed guest TAP interfaces.
- Explicit outbound network destinations and ports.
- Blocking of the cloud metadata address `169.254.169.254`.
- Bounded VSOCK requests, execution concurrency, and captured output.
- Admission limits on resident VMs and concurrent provisioning.
- Resource envelopes in the reusable VM configuration.
- Cleanup of TAP, nftables, socket, IPAM, and VSOCK allocations during normal VM teardown.

These controls should be treated as defense-in-depth rather than a substitute for validating the host kernel, Firecracker configuration, guest image, and deployment environment.

## VM lifecycle

A normal VM provisioning flow is roughly:

1. `Manager.ProvisionVM` acquires a provisioning slot.
2. Shiyao allocates the guest subnet, VSOCK CID, TAP name, and socket path.
3. The VMM creates the TAP device and configures the guest's allowed network destinations in the shared nftables policy.
4. Firecracker starts from the configured kernel/rootfs or resumes from a snapshot.
5. The guest agent accepts VSOCK execution requests.
6. On teardown, Shiyao removes nftables set elements, the TAP device, socket, and IPAM/VSOCK allocations.

The lifecycle is intentionally centralized in the VMM manager so capacity, resource ownership, and cleanup can be coordinated.

## Network policy

Guest forwarding is **default-deny**.

The shared `inet shiyao` nftables policy currently:

- Blocks access to `169.254.169.254` (cloud metadata).
- Allows established and related connections.
- Allows guest DNS to the configured host gateway on UDP port 53.
- Allows the configured host proxy and explicitly configured TCP ports on that gateway.
- Drops other traffic originating from managed TAP interfaces.

Each VM updates nftables set elements rather than creating a dedicated firewall chain. Policy updates are applied as nftables transactions.

Network policy is configured through the VM configuration's outbound-network intent, for example:

```yaml
network:
    allowed_domains: [api.openai.com]
    block_private_ips: true
```

## VSOCK execution

The host connects to the guest agent on VSOCK port `1024`.

Requests carry a protocol version, request ID, command, arguments, environment, and optional timeout. The host-side API exposes both a one-shot execution path and a streaming path:

- `internal/vsock.Exec` — return a bounded execution result.
- `internal/vsock.ExecStream` — deliver newline-delimited output frames followed by a terminal result frame.

Current protocol limits include:

- Requests capped at **1 MiB**.
- At most **4 concurrent executions per guest**.
- Captured stdout capped at **10 MiB**.
- Captured stderr capped at **10 MiB**.
- Streaming frames capped at **64 KiB**.
- A bounded command execution timeout.

The guest agent is responsible for enforcing the execution side of this protocol; host-side callers should still treat command execution as an untrusted operation.

## Capacity and warm instances

`vmm.ManagerLimits` controls the maximum resident VM count and concurrent provisioning operations. When capacity is exhausted, provisioning returns `vmm.ErrBackpressure` rather than allowing unbounded resource consumption.

`vmm.WarmPool` manages leases for prepared running instances. An instance is only returned to the idle pool after the supplied reset operation succeeds. If reset fails, the instance is stopped and evicted from the pool.

Warm pooling is an optimization with an important security implication: the reset operation is part of the reuse boundary. Deployments running hostile workloads should validate that their reset procedure fully establishes the intended clean state before reusing an instance.

## Snapshots and performance

Shiyao supports snapshot resume and provides benchmarking helpers for comparing cold boot and snapshot-resume operations.

`vmm.MeasureBoots` accepts cold-boot and snapshot-resume operations and returns their durations. Run these measurements as privileged integration benchmarks with identical fixtures and shared guest-readiness checks.

Shiyao does **not** currently claim a universal sub-second startup time. Actual latency depends on the host, kernel, Firecracker configuration, guest image, snapshot state, and workload readiness criteria.

## Configuration

`shiyao.yaml` is the declarative description of a reusable snapshot image. It defines the base runtime, language dependencies, resource envelope, environment, and outbound-network intent used when preparing a VM image.

```yaml
version: "v1alpha1"
name: python-agent
description: Python environment for an AI coding agent
runtime:
    os: linux
    distro: ubuntu-22.04
    architecture: x86_64
language:
    name: python
    version: "3.11"
dependencies:
    system: [curl, git]
    pip: [requests]
resources:
    vcpu: 2
    memory_mb: 512
    disk_mb: 1024
env:
    PYTHONUNBUFFERED: "1"
network:
    allowed_domains: [api.openai.com]
    block_private_ips: true
```

Required resource values are `vcpu`, `memory_mb`, and `disk_mb`. They must be positive, with a minimum of 128 MiB memory and 1 GiB disk. Pin dependency versions where reproducibility matters.

The runtime currently targets Linux on `x86_64`.

## Requirements

- Go 1.26.6 or later (see `go.mod`).
- Linux with KVM access (`/dev/kvm`).
- Firecracker for VM integration runs.
- nftables for guest network policy.
- cgroup v2 delegation for guest command resource-limit integration tests.

## Development

```bash
# Run formatting and unit tests
test -z "$(gofmt -l .)"
go test -p 1 ./...

# Build all command binaries
go build ./cmd/...
```

Guest sandbox integration tests require root and the relevant host kernel capabilities:

```bash
sudo -E "$(command -v go)" test -tags=integration ./cmd/guest-agent -v -count=1
```

Tests skip cgroup or OverlayFS assertions when the executing environment does not delegate the necessary kernel capabilities.

## Project status

Shiyao is under active development. The networking, VSOCK, admission-control, warm-pool, and snapshot components are implementation foundations.

Before accepting untrusted workloads in a deployment, validate the complete stack against its target environment, including:

- Linux kernel and KVM configuration.
- Firecracker version and configuration.
- nftables behavior and network policy.
- cgroup v2 delegation and resource enforcement.
- Guest image and guest-agent behavior.
- VM teardown and reset behavior.
- Cold boot and snapshot-resume performance under representative workloads.
